# Как писать тесты для задач TypeScript

Каждая задача раздела имеет файл `tests/<группа>/<задача>.ts`. Он открыт пользователю во вкладке `tests.ts` как учебный материал. Код тестов **никогда не выполняется**, он только проверяется компилятором.

## Формат

```ts
describe("combine", () => {
  test("результат содержит методы всех плагинов", () => {
    const timestamp: number = api.now();
  });

  test("методы вызываются только с аргументами своего типа", () => {
    // @ts-expect-error
    api.random("10");
  });
});
```

- В файле допустимы только вызовы `describe()` (один уровень) и `test()`. Любое вспомогательное — внутри тела `test()`: объявления верхнего уровня конфликтовали бы с именами в решении пользователя.
- В тестах доступны `Equal`, `Expect`, `Prettify`, `test`, `describe`: движок подставляет их автоматически. Эти пять имён зарезервированы — в стартовом коде и эталоне их объявлять нельзя.
- Тест падает, если внутри него есть ошибка компиляции. `// @ts-expect-error` инвертирует проверку: тест падает, когда ошибки **нет**.

## Правила

1. **Проверяйте наблюдаемое поведение типа** (что принимает, что возвращает, что запрещено), а не его форму. `Equal` различает `{ a } & { b }` и `{ a; b }`, `readonly`, `?` и `| undefined` — используйте его, только когда форма и есть суть задачи. Когда форма не важна, сравнивайте нормализованный тип: `Equal<Prettify<typeof value>, { … }>`.
2. На каждый пункт условия — минимум один позитивный и один негативный кейс; всего 3–8 кейсов на задачу.
3. Имя кейса — требование на русском в настоящем времени («random не принимает строку»). Список имён до запуска должен читаться как условие задачи.
4. Опирайтесь только на имена, названные в условии или присутствующие в стартовом коде. Если тесту нужен тип, которого нет в стартовом коде, назовите его в комментарии условия.
5. **Группы 1–3** (Основы, Сужение типов, Дженерики): только вызовы, присваивания с аннотацией (`const n: number = f()`) и `@ts-expect-error`. Без `Equal`, `Expect`, `Prettify`, `ReturnType`, `Parameters`, `Awaited` — пользователь ещё не знает утилитных типов. Присваивание с аннотацией проверяет совместимость, а не точное равенство (`any` его пройдёт), поэтому к каждому позитивному кейсу добавляйте негативный, который `any`-решение провалит.
6. Примеры «это должно быть ошибкой» не оставляйте в стартовом коде и эталонах (ни активными, ни закомментированными): их место — негативные кейсы `@ts-expect-error` в тестах.
7. Если у задачи есть заметно отличающиеся верные решения (`interface` и `type`, перегрузки и union), добавьте их в `solutions-alt/<группа>/<задача>.<n>.ts`: CI требует от них 100% тестов.

## Связь с чек-листом

Пункт чек-листа отмечается автоматически после успешной сдачи, если привязать его к тестам в `data/groups/*.ts`:

```ts
linked("random принимает только число", "методы вызываются только с аргументами своего типа"),
```

Привязывайте пункт только тогда, когда названные тесты **полностью** его проверяют. Пункты о приёмах реализации («использует infer», «без приведений типов») оставляйте ручными.

## Что гарантирует CI

`src/entities/task/model/typescriptCurriculumTests.test.ts` для каждой задачи проверяет: тесты корректно оформлены, эталон и альтернативные эталоны проходят 100%, стартовый код — нет, имена в `linked()` существуют, нет «осиротевших» тестов, а в группах 1–3 не используются утилитные типы.
