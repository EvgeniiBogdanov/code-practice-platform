# Разбор задачи: «Разные формы события»

## 1. Что дано

Обработчик принимает события двух видов. Для клика он выводит координаты `x` и `y`, а для нажатия клавиши — поле `key`. В заготовке уже есть проверки `event.type`, но сама структура событий не описана.

Нужно связать значение `type` с набором доступных данных.

## 2. Что нужно получить

| Вид события | Обязательные данные |
| --- | --- |
| `"click"` | `x: number`, `y: number` |
| `"keypress"` | `key: string` |

В ветке клика координаты должны быть известны как числа, а в ветке клавиши `key` — как строка. Событие клика без координат не должно соответствовать контракту.

## 3. Почему один объект с необязательными полями неудобен

Можно было бы объявить общий тип с `type: "click" | "keypress"`, `x?`, `y?` и `key?`. Но он разрешил бы бессмысленный объект `{ type: "click" }` без координат.

Кроме того, проверка `type` не сделала бы `x` обязательным: в этом описании нет связи между видом события и присутствием поля. Пришлось бы добавлять повторные проверки внутри обработчика.

Правильнее представить событие как один из двух цельных вариантов, каждый со своими обязательными данными.

## 4. Решение по шагам

### Шаг 1. Описать отдельные варианты

Для `ClickEvent` значение `type` — именно литерал `"click"`, для `KeyPressEvent` — `"keypress"`. Если в обоих интерфейсах написать просто `string`, различающий признак потеряется.

### Шаг 2. Объединить варианты

`ClickEvent | KeyPressEvent` означает, что аргумент соответствует одному из описаний. Общее поле `type` с разными литеральными значениями называется **дискриминатором**: по нему TypeScript различает участников объединения.

### Полный код

```ts
interface ClickEvent {
  type: "click";
  x: number;
  y: number;
}

interface KeyPressEvent {
  type: "keypress";
  key: string;
}

type AppEvent = ClickEvent | KeyPressEvent;

const handleEvent = (event: AppEvent): void => {
  if (event.type === "click") {
    console.log(event.x, event.y);
  } else if (event.type === "keypress") {
    console.log(event.key);
  }
};
```

## 5. Разбор вызовов «вживую»

```ts
handleEvent({ type: "click", x: 10, y: 20 });
// Выводит 10 и 20.

handleEvent({ type: "keypress", key: "Enter" });
// Выводит Enter.
```

В первом вызове условие выбирает `ClickEvent`. Тип всего объекта сужается, поэтому `x` и `y` доступны без дополнительных утверждений и проверок на отсутствие.

Во втором вызове первая ветка пропускается, а проверка `"keypress"` выбирает `KeyPressEvent`. Поля `key` достаточно для заданного действия. Обращение к `event.x` в этой ветке было бы ошибкой типов.

## 6. Что будет при расширении набора событий

Предположим, добавляется вариант `"focus"`. Его нужно включить в `AppEvent` и предусмотреть поведение обработчика. Само текущее тело с двумя `if` не гарантирует, что новый вариант будет обработан: он может просто пройти мимо обеих веток.

Когда нужна обязательная обработка всех вариантов, используют `switch` и проверку остатка через `never`. После веток всех известных событий никакого варианта остаться не должно; при добавлении нового типа эта гарантия нарушится и станет видна в коде. Для двух событий из упражнения текущих веток достаточно.

## 7. Важные детали и частые ошибки

- Поле-дискриминатор должно быть общим по имени и различаться литеральными значениями.
- Не делайте координаты необязательными в `ClickEvent`: клик в этом контракте всегда содержит обе координаты.
- Объединение `|` описывает альтернативные формы. Пересечение `&` потребовало бы совместить оба несовместимых значения `type` в одном объекте.
- Эти интерфейсы описывают прикладные данные упражнения. Они не являются автоматически встроенными DOM-событиями `MouseEvent` или `KeyboardEvent`.
- Внешний JSON нужно проверить до передачи в `handleEvent`: аннотация параметра сама не создаёт runtime-валидатор.

## 8. Что запомнить

Дискриминируемое объединение хранит связь между видом события и его данными. Проверка одного поля сужает весь объект, поэтому внутри каждой ветки доступны именно те свойства, которые нужны этому событию.
