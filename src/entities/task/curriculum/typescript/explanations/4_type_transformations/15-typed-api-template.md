# Разбор задачи: «Общий шаблон API»

## 1. Что дано

Два объекта описывают API. У обоих есть строковое поле `entity` и объект `endpoints`. Каждый endpoint содержит HTTP-метод и URL. Различаются имена операций:

- у `vtemplateObject` — `getVtemplates` и `postVtemplates`;
- у `reportObject` — `getReports` и `putReports`.

Набор операций каждого объекта заранее известен. Именно эту информацию нужно сохранить в типах.

## 2. Что нужно получить

Нужен общий шаблон, который можно настроить собственным набором ключей. Он должен требовать все операции конкретного API, обнаруживать опечатки в их именах и сохранять одинаковую структуру endpoint.

Например, `reportObject.endpoints.getReports` доступен, а `reportObject.endpoints.getVtemplates` не должен считаться существующим полем.

## 3. Почему Record<string, Endpoint> слишком широк

Словарь с ключом `string` сообщает: «здесь могут быть произвольные строковые имена». Он не требует наличия `getReports` и `putReports` и не отражает закрытый набор операций конкретного API.

Повторять две полные структуры тоже не нужно: общая форма у них одинаковая. Отличие удобно вынести в параметр типа `K`, который будет объединением разрешённых имён.

## 4. Решение по шагам

### Шаг 1. Описать один endpoint

`HttpMethod` задаёт допустимые методы, а `Endpoint` объединяет метод с адресом. Это устраняет повторение одинаковых полей внутри каждой операции.

### Шаг 2. Построить поля из набора K

```ts
interface ApiObject<K extends string> {
  entity: string;
  endpoints: {
    [P in K]: Endpoint;
  };
}
```

`K extends string` ограничивает имена операций строками. Конструкция `[P in K]` — отображаемый тип, или mapped type. Можно читать её как «для каждого имени `P` из `K` создать поле типа `Endpoint`».

Это перебор на уровне типов. Цикл JavaScript не появляется, реальные объекты по-прежнему нужно написать самостоятельно.

### Полный код

```ts
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE";

interface Endpoint {
  method: HttpMethod;
  url: string;
}

interface ApiObject<K extends string> {
  entity: string;
  endpoints: {
    [P in K]: Endpoint;
  };
}

type VtemplateObject = ApiObject<"getVtemplates" | "postVtemplates">;
type ReportObject = ApiObject<"getReports" | "putReports">;

const vtemplateObject: VtemplateObject = {
  entity: "vtemplate",
  endpoints: {
    getVtemplates: { method: "GET", url: "vtemplate" },
    postVtemplates: { method: "POST", url: "vtemplate" },
  },
};

const reportObject: ReportObject = {
  entity: "report",
  endpoints: {
    getReports: { method: "GET", url: "report" },
    putReports: { method: "PUT", url: "report" },
  },
};
```

## 5. Разворачиваем шаблон для report

Подставим `K = "getReports" | "putReports"`:

```ts
// endpoints: {
//   getReports: Endpoint;
//   putReports: Endpoint;
// }
```

Теперь отсутствие `putReports` в литерале объекта — ошибка, потому что поле обязательное. Опечатка `getReport` тоже не заменит нужный `getReports`. При обращении через точку редактор знает именно два названия.

Для `VtemplateObject` тот же шаблон строит другой набор полей. Общая структура переиспользуется, но ключи одного API не переходят в другой.

## 6. Вариант через встроенную утилиту

Вместо `{ [P in K]: Endpoint }` можно написать `Record<K, Endpoint>`. Здесь это равнозначная краткая форма.

Критично не само слово `Record`, а его первый параметр. `Record<K, Endpoint>` с конечным объединением сохраняет обязательные имена. `Record<string, Endpoint>` делает набор открытым и не выполняет главное требование упражнения.

## 7. Важные детали и частые ошибки

- Знак `?` после `[P in K]` сделал бы все операции необязательными. В текущем условии это не требуется.
- Все методы имеют тип `HttpMethod`. Шаблон не связывает префикс `get` с единственным методом `GET`; такое правило пришлось бы описывать дополнительно.
- `entity: string` не связывает имя сущности с `url`. Здесь проверяется структура, а не бизнес-согласованность всех строк.
- Проверка лишних полей особенно заметна у свежих литералов объектов. Структурная типизация в целом не превращает контракт в универсальную проверку отсутствия дополнительных свойств во внешних данных.
- Не расширяйте конкретный набор ключей до `string` до применения шаблона: после потери этой информации тип уже не восстановит исходные имена.

## 8. Что запомнить

Отображаемый тип превращает объединение ключей в объектную структуру. Один дженерик позволяет переиспользовать описание API, сохраняя обязательные операции каждого конкретного объекта.
