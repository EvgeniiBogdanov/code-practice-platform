# Разбор задачи: «Структурная типизация»

## 1. Что дано

Две ситуации, которые удивляют тех, кто пришёл из Java или C#:

1. Переменная `point3d` с лишним полем `z` подходит к `Point`, а тот же объект, написанный литералом прямо в вызове, — нет.
2. `saveCelsius` спокойно принимает `Fahrenheit`, хотя это разные интерфейсы.

## 2. Что нужно получить

- `printPoint` явно принимает точки с дополнительными полями в любой форме вызова.
- `Fahrenheit` нельзя передать туда, где ожидается `Celsius`.

## 3. Структурная, а не номинальная типизация

В TypeScript совместимость определяется **формой** значения, а не именем типа. Значение подходит к `Point`, если у него есть `x: number` и `y: number`. Лишние поля не мешают: объект с `z` по-прежнему является точкой на плоскости. Это называют «утиной типизацией»: если оно крякает как утка — это утка.

Поэтому `Celsius` и `Fahrenheit` — фактически один тип `{ value: number }`. Имя интерфейса для проверки совместимости значения не имеет.

## 4. Почему литерал с z — ошибка

Это отдельный механизм — **проверка лишних свойств** (excess property check). Она срабатывает только для «свежего» объектного литерала, который сразу присваивается в место с известным типом. Логика такая: если вы пишете литерал прямо в вызове и указываете поле, которого нет в типе, скорее всего это опечатка (`{ x: 1, yy: 2 }`). У переменной `point3d` литерал уже не «свежий»: она могла понадобиться где-то ещё целиком, поэтому лишние поля разрешены.

## 5. Решение по шагам

### Шаг 1. Параметр типа вместо конкретного типа

```ts
const printPoint = <T extends Point>(point: T): void => { ... };
```

Теперь тип параметра — точный тип аргумента `T`, например `{ x: number; y: number; z: number }`. Ограничение `extends Point` проверяет, что `x` и `y` есть и они числа. Проверка лишних свойств к параметру типа не применяется, поэтому литерал с `z` проходит.

Что **не** подходит: `point: Point & Record<string, unknown>` или индексная сигнатура в самом `Point` — они меняют модель точки для всего кода, а не только для этой функции. А `point: any` ослабляет проверку `x` и `y`.

### Шаг 2. Структурное различие для единиц измерения

Если типы должны быть несовместимы, их структуры должны различаться. Самый простой способ — литеральное поле-дискриминатор:

```ts
interface Celsius { unit: "C"; value: number }
interface Fahrenheit { unit: "F"; value: number }
```

`"F"` нельзя присвоить `"C"`, поэтому `saveCelsius(outside)` — ошибка. Поле существует и во время выполнения, поэтому значение можно проверить и в рантайме.

### Полный код

```ts
interface Point {
  x: number;
  y: number;
}

const printPoint = <T extends Point>(point: T): void => {
  console.log(`(${point.x}, ${point.y})`);
};

printPoint({ x: 1, y: 2, z: 3 });

interface Celsius {
  unit: "C";
  value: number;
}

interface Fahrenheit {
  unit: "F";
  value: number;
}

const saveCelsius = (temperature: Celsius): void => {
  console.log(`${temperature.value} °C`);
};
```

## 6. Совместимость функций — тоже структурная

Функция `(x: number) => void` подходит к типу `(x: number, y: number) => void`: она просто проигнорирует второй аргумент. Поэтому в `array.map` можно передать колбэк с одним параметром, хотя `map` передаёт три.

## 7. Частые ошибки

- Думать, что разные имена интерфейсов делают их несовместимыми.
- Считать проверку лишних свойств частью структурной типизации. Это отдельная эвристика для литералов, и обходится она простым выносом литерала в переменную.
- Использовать `{}` как «любой объект». Структурно ему соответствуют даже строки и числа.

## 8. Что запомнить

Совместимость в TypeScript определяется формой. Лишние поля разрешены, кроме свежих литералов. Чтобы типы стали несовместимыми, их структура должна различаться: литеральным полем, а без рантайм-поля — брендом (этот приём будет в разделе прикладных паттернов).
