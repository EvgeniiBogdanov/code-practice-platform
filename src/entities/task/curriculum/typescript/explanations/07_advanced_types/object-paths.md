# Разбор задачи: «Пути к вложенным полям»

## 1. Что дано

Функция `get(obj, "user.address.city")` читает вложенное поле по строковому пути. Без типов можно передать любой путь, а результат — `any`. Такие функции есть в lodash, react-hook-form, i18n-библиотеках. Нужно описать все допустимые пути и тип значения по каждому из них.

## 2. Что нужно получить

| Тип или вызов | Результат |
| --- | --- |
| `Paths<Settings>` | `"user" \| "user.name" \| "user.address" \| "user.address.city" \| "user.address.zip" \| "theme"` |
| `PathValue<Settings, "user.address.zip">` | `number` |
| `get(settings, "user.address.city")` | `string` |
| `get(settings, "user.phone")` | ошибка |

## 3. Paths: рекурсия по ключам

```ts
type Paths<T> = T extends object
  ? {
      [K in keyof T & string]: K | `${K}.${Paths<T[K]>}`;
    }[keyof T & string]
  : never;
```

Разберём по частям:

1. `T extends object` — для примитивов путей нет, результат `never`.
2. Отображаемый тип создаёт для каждого строкового ключа `K` значение: сам ключ **или** ключ, точка и пути внутри `T[K]`.
3. `[keyof T & string]` в конце — индексный доступ по всем ключам: собирает значения всех полей в одно объединение. Это стандартный приём «отображаемый тип → объединение значений».

Почему у листа не появляется `"theme."`? Для `T[K] = "light" | "dark"` `Paths` возвращает `never`, а шаблонная строка с `never` внутри — тоже `never`. Остаётся только `K`.

Вычисление для `user`:

| Уровень | Значение |
| --- | --- |
| `address` | `"city" \| "zip"` → `"address" \| "address.city" \| "address.zip"` |
| `user` | `"user" \| "user.name" \| "user.address" \| "user.address.city" \| "user.address.zip"` |

## 4. PathValue: разбор строки

```ts
type PathValue<T, P extends string> = P extends `${infer Head}.${infer Rest}`
  ? Head extends keyof T
    ? PathValue<T[Head], Rest>
    : never
  : P extends keyof T
    ? T[P]
    : never;
```

Шаблон `${infer Head}.${infer Rest}` отрезает первый сегмент до точки. `Head` захватывает минимальную подстроку до первой точки, `Rest` — всё остальное. Дальше спускаемся в `T[Head]` и разбираем `Rest`. Когда точек не осталось, `P` — последний ключ.

| Шаг | `T` | `P` |
| --- | --- | --- |
| 1 | `Settings` | `"user.address.zip"` |
| 2 | `Settings["user"]` | `"address.zip"` |
| 3 | `...["address"]` | `"zip"` |
| 4 | — | `number` |

## 5. get: строгий фасад и честная реализация

```ts
const get = <T extends object, P extends Paths<T>>(obj: T, path: P): PathValue<T, P> =>
  path.split(".").reduce<unknown>(readKey, obj) as PathValue<T, P>;
```

- `P extends Paths<T>` разрешает только существующие пути, и редактор подсказывает их при вводе.
- Результат — `PathValue<T, P>` для конкретного пути.

Реализация обходит объект во время выполнения, и промежуточные значения честно имеют тип `unknown`. Компилятор не может связать `split(".")` с рекурсивным типом `PathValue`, поэтому в конце стоит одно утверждение. Это осознанный компромисс типового программирования: строгий публичный контракт и изолированное утверждение внутри реализации.

## 6. Ограничения

- **Глубина рекурсии.** Рекурсивные условные типы ограничены (около 50 уровней для обычной рекурсии). Для циклических структур вроде `Node { children: Node[] }` нужен счётчик глубины.
- **Массивы.** Массив — объект, и `keyof` добавит `"length"` и методы. Для массивов пишут отдельную ветку с `${number}`.
- **Производительность.** Для больших моделей объединение путей разрастается и замедляет редактор.

## 7. Частые ошибки

- Забыть `& string` у `keyof T`: числовые и символьные ключи не встраиваются в шаблонную строку.
- Возвращать из отображаемого типа объект, а не объединение значений: забыть `[keyof T & string]` в конце.
- Использовать `any` в `reduce`: утверждение должно быть одно и на выходе, а не размазано по реализации.

## 8. Что запомнить

Рекурсивный отображаемый тип с индексным доступом в конце собирает объединение путей, а шаблон с `infer` разбирает путь обратно. Так строятся типы для форм, переводов и доступа к вложенным данным.
