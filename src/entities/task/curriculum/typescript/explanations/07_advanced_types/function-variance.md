# Разбор задачи: «Вариантность функций»

## 1. Что дано

`Dog` — подтип `Animal`. Обработчик собак `handleDog` присваивается в поле обработчика животных, TypeScript молчит, а вызов с кошкой падает: `dog.bark is not a function`. Нужно понять, почему система типов это пропустила, и закрыть дыру.

## 2. Вариантность: в какую сторону переносится совместимость

Если `Dog` подходит туда, где ожидается `Animal`, что можно сказать о сложных типах, построенных из них?

| Вариантность | Правило | Где возникает |
| --- | --- | --- |
| ковариантность | `Box<Dog>` → `Box<Animal>` | значения «на выходе»: результат, `readonly`-поле |
| контравариантность | `Handler<Animal>` → `Handler<Dog>` | значения «на входе»: параметры функции |
| инвариантность | ни в одну сторону | тип и читается, и записывается |
| бивариантность | в обе стороны | небезопасный компромисс |

**Почему параметры контравариантны.** Где ожидается «обработчик собак», безопасно использовать «обработчик любых животных»: он справится и с собакой. А вот «обработчик собак» на месте «обработчика животных» получит кошку и упадёт. Значит, `(a: Animal) => void` подходит к `(d: Dog) => void`, но не наоборот.

## 3. Почему TypeScript пропустил ошибку

В интерфейсе `onEvent` записан **методом**:

```ts
interface AnimalHandler {
  onEvent(animal: Animal): void;
}
```

Флаг `strictFunctionTypes` (входит в `strict`) включает строгую контравариантную проверку только для **свойств с типом функции**. Методы намеренно проверяются бивариантно. Причина — совместимость: `Array<T>` объявляет `push(item: T)` методом, и без бивариантности `Dog[]` нельзя было бы передать туда, где ожидается `Animal[]`. Огромное количество существующего кода опирается на это поведение.

## 4. Решение по шагам

### Шаг 1. Свойство-функция вместо метода

```ts
interface AnimalHandler {
  onEvent: (animal: Animal) => void;
}
```

Теперь `{ onEvent: handleDog }` — ошибка: `Type 'Animal' is not assignable to type 'Dog'`. Это простое правило многих кодстайлов (и правило ESLint `@typescript-eslint/method-signature-style`): описывать колбэки в интерфейсах свойствами.

### Шаг 2. Аннотация вариантности для Box

```ts
interface Box<out T> {
  readonly value: T;
}
```

`out T` объявляет, что `T` только «выходит» из `Box`: его можно прочитать, но нельзя передать внутрь. Поэтому `Box<Dog>` подходит к `Box<Animal>`. TypeScript проверяет аннотацию: если добавить метод `set(value: T): void`, объявление станет ошибкой, потому что `T` появится во входной позиции.

Обратная аннотация `in T` объявляет контравариантность, а `in out T` — инвариантность.

### Полный код

```ts
interface AnimalHandler {
  onEvent: (animal: Animal) => void;
}

const handleAnimal = (animal: Animal): void => {
  console.log(animal.name);
};

const animalHandler: AnimalHandler = { onEvent: handleAnimal };

interface Box<out T> {
  readonly value: T;
}

const dogBox: Box<Dog> = { value: { name: "Рекс", bark: () => console.log("Гав") } };
const animalBox: Box<Animal> = dogBox;
```

## 5. Зачем нужны in и out, если TypeScript вычисляет вариантность сам

1. **Документация и защита.** Аннотация фиксирует намерение: случайное использование `T` не в той позиции станет ошибкой в объявлении, а не где-то у потребителей.
2. **Скорость.** Для сложных рекурсивных типов вычисление вариантности дорогое, а иногда неточное. Явная аннотация избавляет компилятор от этой работы.

## 6. Известная небезопасность: ковариантные массивы

```ts
const dogs: Dog[] = [];
const animals: Animal[] = dogs; // разрешено
animals.push({ name: "Кот" }); // компилируется, но в массиве собак кошка
```

Изменяемые массивы на самом деле должны быть инвариантными, но TypeScript сознательно делает их ковариантными ради удобства. `readonly Animal[]` этой проблемы лишён: в него нельзя записать. Это хороший пример для собеседования о границах надёжности системы типов.

## 7. Частые ошибки

- Объяснять дыру «ошибкой TypeScript», а не осознанной бивариантностью методов.
- Думать, что `strict` делает все проверки функций строгими.
- Ставить `out` на тип, который используется и для чтения, и для записи.

## 8. Что запомнить

Результаты ковариантны, параметры контравариантны. Методы проверяются бивариантно даже в strict-режиме, поэтому колбэки в интерфейсах описывают свойствами. Аннотации `in` и `out` фиксируют вариантность явно и ускоряют проверку.
