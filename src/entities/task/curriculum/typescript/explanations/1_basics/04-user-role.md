# Разбор задачи: «Роль пользователя»

## 1. Что дано

В `User` уже описаны имя и возраст. Интерфейс `UserWithRole` повторяет эти поля и добавляет `role: string`. Объект `admin` содержит имя `"Alice"`, возраст `30` и роль `"admin"`.

Недостатка два: общие поля продублированы, а роль может оказаться любой строкой, включая опечатку `"admn"`.

## 2. Что нужно получить

`UserWithRole` должен сохранять все требования `User` и дополнительно требовать одну из двух ролей: `"admin"` или `"user"`. При изменении базового описания пользователя общие поля должны обновляться в одном месте.

## 3. Первая идея: перечислить всё ещё раз

Можно вручную исправить только поле роли в копии интерфейса. Для маленького примера это работает, но две независимые копии `name` и `age` легко разойдутся. Например, к `User` добавят обязательный `email`, а `UserWithRole` забудут обновить.

Лучше выразить отношение прямо: «пользователь с ролью — это пользователь плюс одно поле». Для интерфейсов это делает `extends`.

## 4. Решение по шагам

### Шаг 1. Описать конечный набор ролей

```ts
type Role = "admin" | "user";
```

`"admin"` здесь — строковый литеральный тип, допускающий одно значение. Оператор `|` объединяет варианты: подходит либо `"admin"`, либо `"user"`. Это не логическое `||` из JavaScript и не строка `"admin | user"`.

### Шаг 2. Расширить базовый интерфейс

`interface UserWithRole extends User` включает в новый интерфейс поля `User`. Внутри остаётся объявить только `role`.

### Полный код

```ts
interface User {
  name: string;
  age: number;
}

type Role = "admin" | "user";

interface UserWithRole extends User {
  role: Role;
}

const admin: UserWithRole = {
  name: "Alice",
  age: 30,
  role: "admin",
};
```

## 5. Что TypeScript видит у объекта

При чтении `UserWithRole` можно мысленно развернуть его так:

```ts
// Структура UserWithRole:
// {
//   name: string;
//   age: number;
//   role: "admin" | "user";
// }

admin.role = "user";
// admin.role = "owner"; // Такой роли нет в Role.
```

Объект обязан содержать и `name`, и `age`, и `role`. Значение роли можно поменять на другой разрешённый вариант: условие не требует делать поле неизменяемым.

Если позже добавить `"moderator"` в `Role`, новый вариант станет доступен во всех местах, использующих этот тип. Если добавить обязательное поле в `User`, его автоматически потребует и `UserWithRole`.

## 6. Важные детали и частые ошибки

- `role: string` разрешает опечатки; `role: Role` отражает конкретные бизнес-правила этого упражнения.
- Аннотация `: UserWithRole` у объекта даёт контекст его полям. Без контекста поле `role` у обычного изменяемого объекта может получить широкий тип `string`, даже если сначала содержит `"admin"`.
- `extends` у интерфейсов описывает совместимость структур. Он не создаёт прототипы, конструкторы или объекты во время выполнения, в отличие от наследования классов.
- Литеральный тип не проверяет полученную из API строку. Внешнее значение нужно отдельно сопоставить с разрешёнными ролями, прежде чем считать его `Role`.
- Новый интерфейс можно использовать там, где требуется `User`: у него есть все нужные базовые поля. Обратное неверно, потому что обычный `User` не обязан иметь роль.

## 7. Что запомнить

Общий интерфейс хранит общие поля, `extends` выражает их переиспользование, а объединение литералов задаёт конечный словарь допустимых значений. Вместе они устраняют дублирование и делают роль точной.
