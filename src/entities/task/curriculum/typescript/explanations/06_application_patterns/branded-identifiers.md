# Разбор задачи: «Единица измерения»

## 1. Что дано

Идентификатор пользователя и идентификатор заказа оба представлены строками. Функции `getUserById` и `getOrderById` должны принимать каждый свой вид идентификатора.

Без дополнительного описания вызов `getUserById(orderId)` выглядит для TypeScript допустимым: ожидается строка и передана строка. Но по смыслу это ошибка.

## 2. Что нужно получить

Нужны два несовместимых типа: `UserId` и `OrderId`. Значения по-прежнему должны быть обычными строками при выполнении программы, без упаковки в классы или объекты.

| Вызов | Ожидание |
| --- | --- |
| `getUserById(userId)` | Допустим |
| `getOrderById(orderId)` | Допустим |
| `getUserById(orderId)` | Ошибка типов |
| `getOrderById(userId)` | Ошибка типов |

## 3. Почему разных имён type недостаточно

```ts
type PlainUserId = string;
type PlainOrderId = string;
```

Эти псевдонимы помогают читать код, но оба обозначают тот же `string`. TypeScript в основном использует структурную совместимость: разные имена сами по себе не делают одинаковые структуры несовместимыми.

Поэтому нужно добавить различающий признак в **структуру типа**, сохранив исходное значение. Такой приём называется брендингом, а типы — branded types.

## 4. Решение по шагам

### Шаг 1. Создать общий Brand

```ts
type Brand<T, B extends string> = T & { readonly __brand: B };
```

`T` — исходный тип, `B` — строковая метка смысла значения. Пересечение `&` добавляет к требованиям исходного типа признак `__brand`. Для пользователя и заказа метки будут разными литералами.

Поле служит различению в системе типов. Приведённые ниже фабрики не добавляют его к строке во время выполнения.

### Шаг 2. Объявить два вида идентификаторов

`Brand<string, "UserId">` и `Brand<string, "OrderId">` имеют одинаковую строковую основу, но разные обязательные метки. Именно метки делают эти типы несовместимыми друг с другом.

### Шаг 3. Создавать идентификаторы в выделенных функциях

Обычная строка не содержит типовой метки. В минимальном решении переход выражен утверждением типа внутри `toUserId` или `toOrderId`. Остальной код получает готовые значения и передаёт их в функции с точными контрактами.

### Полный код

```ts
type Brand<T, B extends string> = T & { readonly __brand: B };

type UserId = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

const toUserId = (id: string): UserId => {
  return id as UserId;
};

const toOrderId = (id: string): OrderId => {
  return id as OrderId;
};

const getUserById = (id: UserId): void => {
  // Здесь могла бы быть загрузка пользователя.
};

const getOrderById = (id: OrderId): void => {
  // Здесь могла бы быть загрузка заказа.
};

const userId = toUserId("user-1");
const orderId = toOrderId("order-1");

getUserById(userId);
getOrderById(orderId);
// getUserById(orderId); // OrderId несовместим с UserId.
// getOrderById(userId); // UserId несовместим с OrderId.
```

## 5. Разбор несовместимости по шагам

При `getUserById(orderId)` TypeScript сравнивает ожидаемый `UserId` с фактическим `OrderId`:

1. Строковая часть совпадает.
2. Ожидаемая метка — `__brand: "UserId"`.
3. Переданная метка — `__brand: "OrderId"`.
4. Литералы различаются, значит структуры несовместимы и вызов отвергается.

В JavaScript обе метки исчезают вместе с описаниями типов. `typeof userId` по-прежнему равно `"string"`, а значение остаётся `"user-1"`.

Брендированную строку можно использовать как обычную строку, например передать в вывод или строковую операцию. Обратное присваивание обычной строки в `UserId` не разрешено без специального перехода.

## 6. Где должна находиться проверка формата

Текущие `toUserId` и `toOrderId` ничего не проверяют. `as UserId` означает «считай значение этим типом», а не «докажи корректность идентификатора».

Если предметная область, например, запрещает пустые идентификаторы, фабрику можно дополнить настоящим условием:

```ts
const toNonEmptyUserId = (id: string): UserId => {
  if (id.trim().length === 0) {
    throw new Error("Идентификатор пользователя не должен быть пустым");
  }

  return id as UserId;
};
```

Это только пример дополнительного правила. Формат, префикс и существование пользователя исходным условием не определены. Проверка непустой строки не доказывает наличие записи на сервере.

Фабрика — место осознанного перехода между сырым значением и доменным типом. Не следует произвольно вызывать её для повторного брендинга уже полученных идентификаторов другого назначения.

## 7. Важные детали и частые ошибки

- Метка должна различаться: одинаковый бренд у пользователя и заказа не решит задачу.
- Не делайте `__brand` необязательным, если нужно запретить прямое присваивание обычной строки. Это ослабит контракт.
- Не читайте `userId.__brand` в расчёте увидеть реальное поле: в данном способе создания оно существует только для системы типов.
- Строковая операция вроде конкатенации обычно возвращает обычный `string`. Смысл доменного идентификатора после изменения строки нужно устанавливать заново.
- JSON не сохраняет типовой бренд. После чтения внешних данных нужен новый переход через соответствующую границу создания.
- Прямое утверждение типа в произвольном месте может обойти защиту. Брендинг помогает предотвращать случайную путаницу при соблюдении контрактов, а не делает значение неподделываемым.

## 8. Что запомнить

Бренд добавляет смысловую различимость к одинаковым примитивам. Разные ID остаются строками во время выполнения, но становятся разными контрактами для функций; фабрики сосредотачивают создание таких значений и возможную проверку их формата.
