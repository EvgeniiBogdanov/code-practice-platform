## Идея простыми словами

Представь, что ты играешь в игру "угадай число от 1 до 100". Ты называешь
число, а тебе говорят: "больше" или "меньше". Самая глупая стратегия —
называть числа по порядку: 1, 2, 3, 4... Это может занять до 100 попыток.

Умная стратегия — каждый раз называть **число посередине** оставшегося
диапазона. Сначала 50. Если "больше" — значит, число от 51 до 100, следующая
попытка — 75. Если "меньше" — значит, число от 51 до 74, следующая попытка —
62. И так далее. Каждая попытка отсекает **половину** оставшихся вариантов.
Даже для 100 чисел тебе хватит всего 7 попыток, а не 100.

Это и есть бинарный поиск: на каждом шаге мы смотрим на **средний элемент**
и, сравнивая его с искомым значением, отбрасываем **половину** данных, в
которой точно не может быть ответа.

## Зачем это нужно

Допустим, у тебя отсортированный массив из миллиона чисел, и нужно понять,
есть ли в нём число `42`.

**Наивный способ (линейный поиск)** — пройтись по массиву от начала до
конца и сравнить каждый элемент. В худшем случае (если числа нет или оно в
самом конце) — миллион сравнений. Сложность `O(n)`.

**Бинарный поиск** — за счёт того, что массив отсортирован, каждое сравнение
отбрасывает половину оставшихся данных. Для миллиона элементов хватит всего
около **20 сравнений** (`log₂(1 000 000) ≈ 20`). Сложность `O(log n)`.

Разница между `O(n)` и `O(log n)` на больших объёмах данных огромна — это
одна из причин, почему бинарный поиск — один из самых важных алгоритмов в
программировании, а не просто "олимпиадная теория".

## Главное условие: массив должен быть отсортирован

Бинарный поиск работает **только** там, где можно на каждом шаге однозначно
сказать: "искомое значение точно левее середины" или "точно правее". Это
возможно только если данные упорядочены (по возрастанию или по убыванию).

Если массив не отсортирован, бинарный поиск даст неверный результат — сначала
нужно отсортировать массив (`O(n log n)`), и только потом искать (`O(log n)`).
Если поиск выполняется **один раз**, сортировка ради одного бинарного поиска
не имеет смысла — быстрее пройтись линейно. А вот если поисков **много**, а
массив один и тот же — сортировка один раз того стоит.

## Базовая реализация на JavaScript

Классический бинарный поиск: ищем индекс элемента `target` в отсортированном
по возрастанию массиве `arr`. Если элемента нет — возвращаем `-1`.

```js
const binarySearch = (arr, target) => {
  let left = 0;
  let right = arr.length - 1;

  while (left <= right) {
    const mid = Math.floor((left + right) / 2);

    if (arr[mid] === target) {
      return mid; // нашли — сразу возвращаем индекс
    } else if (arr[mid] < target) {
      left = mid + 1; // искомое точно правее середины
    } else {
      right = mid - 1; // искомое точно левее середины
    }
  }

  return -1; // не нашли
};

const arr = [1, 3, 5, 7, 9, 11, 13, 15];
console.log(binarySearch(arr, 9));  // 4
console.log(binarySearch(arr, 1));  // 0
console.log(binarySearch(arr, 15)); // 7
console.log(binarySearch(arr, 4));  // -1 (такого числа нет в массиве)
```

Разберём логику построчно:

- **`left` и `right`** — это границы того "куска" массива, где мы ещё можем
  найти ответ. В начале это весь массив: от `0` до `arr.length - 1`.
- **`mid`** — индекс среднего элемента текущего диапазона.
- **`while (left <= right)`** — цикл продолжается, пока границы не
  "перехлестнулись" (то есть пока в диапазоне есть хотя бы один элемент).
  Обрати внимание на знак `<=` — именно **меньше или равно**, чтобы проверить
  последний оставшийся элемент, когда `left === right`.
- **`arr[mid] === target`** — нашли совпадение, возвращаем индекс.
- **`arr[mid] < target`** — средний элемент меньше искомого, значит искомое
  лежит правее. Сдвигаем левую границу: `left = mid + 1` (сам `mid` уже
  проверили, его включать не нужно).
- **`arr[mid] > target`** — средний элемент больше искомого, значит искомое
  лежит левее. Сдвигаем правую границу: `right = mid - 1`.
- **`return -1`** — если цикл завершился, а совпадение не нашлось — числа в
  массиве нет.

## Пошаговая трассировка

Проследим, как ищется число `7` в массиве `[1, 3, 5, 7, 9, 11, 13]`:

| Шаг | left | right | mid | arr[mid] | Сравнение | Действие |
|---|---|---|---|---|---|---|
| 1 | 0 | 6 | 3 | 7 | 7 === 7 | Нашли! Возвращаем 3 |

Нашлось за 1 шаг, потому что 7 случайно оказалось ровно посередине.

Теперь поищем число `11` в том же массиве:

| Шаг | left | right | mid | arr[mid] | Сравнение | Действие |
|---|---|---|---|---|---|---|
| 1 | 0 | 6 | 3 | 7 | 7 < 11 | 11 правее → `left = 3 + 1 = 4` |
| 2 | 4 | 6 | 5 | 11 | 11 === 11 | Нашли! Возвращаем 5 |

Всего 2 шага для массива из 7 элементов.

А теперь поищем число `4` (которого нет в массиве):

| Шаг | left | right | mid | arr[mid] | Сравнение | Действие |
|---|---|---|---|---|---|---|
| 1 | 0 | 6 | 3 | 7 | 7 > 4 | 4 левее → `right = 3 - 1 = 2` |
| 2 | 0 | 2 | 1 | 3 | 3 < 4 | 4 правее → `left = 1 + 1 = 2` |
| 3 | 2 | 2 | 2 | 5 | 5 > 4 | 4 левее → `right = 2 - 1 = 1` |

После шага 3: `left = 2`, `right = 1`. Условие `left <= right` нарушилось
(`2 <= 1` — ложь), цикл завершился, вернули `-1`. Всё корректно.

## Сложность алгоритма

- **По времени:** `O(log n)` — на каждом шаге размер задачи делится на 2.
  Для массива из 1 000 элементов нужно не более 10 шагов, для 1 000 000 —
  не более 20 шагов.
- **По дополнительной памяти:** `O(1)` — алгоритм хранит всего 3 переменные
  (`left`, `right`, `mid`) независимо от размера массива.

## Подводные камни

### 1. Переполнение целых чисел при вычислении `mid`

В большинстве языков запись `(left + right) / 2` при очень больших массивах
(миллиарды элементов) может привести к переполнению целого числа (integer
overflow), потому что сумма `left + right` выйдет за максимальное значение
`int32`.

В JavaScript все числа по умолчанию имеют тип `double` (64-битное число с
плавающей точкой), поэтому явного переполнения не произойдёт, но безопасная
запись считается стандартом хорошего тона на собеседованиях:

```js
// Классическая безопасная запись:
const mid = Math.floor(left + (right - left) / 2);

// Битовый сдвиг (работает как деление на 2 с округлением вниз, быстро):
const mid = (left + right) >> 1;
```

### 2. Бесконечный цикл из-за неправильного обновления границ

Если забыть `+ 1` или `- 1` и написать `left = mid` или `right = mid` в
классическом цикле `while (left <= right)`, то для массива из двух элементов
алгоритм может зациклиться навсегда (когда `left` и `right` перестанут
сдвигаться, а `mid` будет оставаться одним и тем же).

Правило простое: в классическом поиске **всегда** `left = mid + 1` и
`right = mid - 1`.

### 3. `<=` vs `<` в условии цикла

- `while (left <= right)` — используется, когда диапазон поиска включает обе
  границы `[left, right]`, и обновление идёт через `mid + 1` / `mid - 1`.
- `while (left < right)` — используется в задачах поиска **границы** (lower/upper
  bound, поиск по ответу), когда одна из границ обновляется как `right = mid`.

## Бинарный поиск не только по массиву — поиск по ответу

Это важнейшее обобщение: бинарным поиском можно искать не только элемент в
массиве, но и **числовой ответ задачи**, если функция ответа **монотонна**
(например: "при скорости X мы успеем? — да/нет", где при большей скорости мы
всегда успеваем, а при меньшей — нет).

Пример: поиск квадратного корня числа `x` (`Math.sqrt(x)` без встроенной функции):

```js
const mySqrt = (x) => {
  if (x < 2) return x;

  let left = 1;
  let right = Math.floor(x / 2);
  let ans = 1;

  while (left <= right) {
    const mid = Math.floor(left + (right - left) / 2);

    if (mid * mid === x) return mid;

    if (mid * mid < x) {
      ans = mid; // запоминаем подходящий кандидат
      left = mid + 1; // пробуем найти больше
    } else {
      right = mid - 1; // перелёт, ищем меньше
    }
  }

  return ans;
};

console.log(mySqrt(4)); // 2
console.log(mySqrt(8)); // 2 (так как 2^2 = 4 <= 8, а 3^2 = 9 > 8)
```

Здесь нет исходного массива — диапазон поиска `[1, x / 2]` виртуальный, и мы
бинарным поиском находим наибольшее число, квадрат которого не превышает `x`.

## Классические задачи

### 1. Search Insert Position (LeetCode 35) — куда вставить элемент

Дан отсортированный массив и число `target`. Если оно есть в массиве —
вернуть его индекс. Если нет — вернуть индекс, куда его нужно было бы
вставить, чтобы массив остался отсортированным.

```js
const searchInsert = (nums, target) => {
  let left = 0;
  let right = nums.length - 1;

  while (left <= right) {
    const mid = Math.floor((left + right) / 2);

    if (nums[mid] === target) return mid;
    if (nums[mid] < target) left = mid + 1;
    else right = mid - 1;
  }

  return left;
};

console.log(searchInsert([1, 3, 5, 6], 5)); // 2
console.log(searchInsert([1, 3, 5, 6], 2)); // 1
console.log(searchInsert([1, 3, 5, 6], 7)); // 4
console.log(searchInsert([1, 3, 5, 6], 0)); // 0
```

### 2. Поиск первого вхождения (Lower Bound) — работа с дубликатами

```js
const lowerBound = (arr, target) => {
  let left = 0;
  let right = arr.length;

  while (left < right) {
    const mid = Math.floor((left + right) / 2);

    if (arr[mid] < target) {
      left = mid + 1;
    } else {
      right = mid;
    }
  }

  return left;
};

const arrDup = [1, 2, 2, 2, 3, 4, 5];
console.log(lowerBound(arrDup, 2)); // 1
```

## Бинарный поиск vs линейный поиск — когда что использовать

| Признак | Линейный поиск | Бинарный поиск |
|---|---|---|
| Массив должен быть отсортирован? | Нет | Да, обязательно |
| Сложность | O(n) | O(log n) |
| Подходит для одного разового поиска в неотсортированных данных? | Да | Нет (сортировка съест весь выигрыш) |
| Подходит для многократного поиска в одном и том же массиве? | Плохо масштабируется | Отлично, особенно на больших данных |
| Работает не только с массивами (поиск по ответу)? | Не типично | Да, это отдельная мощная техника |
