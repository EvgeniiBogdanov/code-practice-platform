# Разбор задачи: Linked List Cycle (LeetCode 141)

## Какой алгоритм используется

**Floyd's Cycle Detection Algorithm** — алгоритм обнаружения цикла Флойда, также известный как **«алгоритм черепахи и зайца»** (Tortoise and Hare). Это частный случай более общего паттерна **Two Pointers** (два указателя), где указатели движутся по одной и той же структуре, но с разной скоростью.

## Суть задачи простыми словами

Дана голова (`head`) односвязного списка. Нужно определить: есть ли в этом списке **цикл** — то есть можно ли, постоянно переходя по ссылкам `next`, рано или поздно снова попасть на уже посещённый узел (список "зацикливается" сам на себя, а не заканчивается на `null`).

Обычный список — это прямая дорога с тупиком в конце:

```
1 → 2 → 3 → 4 → null
```

Список с циклом — это дорога, часть которой оказывается "закольцована", как петля:

```
1 → 2 → 3 → 4
        ↑    ↓
        6 ← 5
```

Если идти по такому списку, вы никогда не дойдёте до `null` — будете бесконечно кружить по петле (3 → 4 → 5 → 6 → 3 → 4 → ...).

**Важный нюанс условия**: `pos` (индекс узла, к которому прикрепляется хвост) используется только для того, чтобы **построить** тестовый список с циклом, но не передаётся в саму функцию `hasCycle` — у вас нет прямого доступа к этой информации, только `head`, и определять наличие цикла нужно исключительно обходом по ссылкам `next`.

## Идея решения: два указателя с разной скоростью

Представьте два бегуна на круговой трассе: один бежит **в два раза быстрее** другого (черепаха — 1 шаг за раз, заяц — 2 шага за раз).

- Если трасса **не замкнута в круг** (обычный список без цикла) — быстрый бегун (заяц) просто первым добежит до финиша (`null`), и никакого "нагона" не произойдёт.
- Если трасса **замкнута в круг** (список с циклом) — быстрый бегун рано или поздно **обгонит** медленного на целый круг и они снова окажутся в одной точке — то есть указатели `slow` и `fast` в какой-то момент совпадут (`slow === fast`).

Это и есть весь алгоритм: если указатели когда-нибудь встретятся — цикл есть; если быстрый указатель дошёл до конца списка (`null`) раньше, чем встретился с медленным — цикла нет.

## Пошаговый разбор решения `hasCycle`

```js
const hasCycle = (head) => {
  let slow = head;
  // 1. "Черепаха" — движется на 1 узел за шаг. Стартует с головы списка.

  let fast = head;
  // 2. "Заяц" — движется на 2 узла за шаг. Тоже стартует с головы списка.

  while (fast && fast.next) {
    // 3. Продолжаем, пока у "зайца" есть куда идти дальше на 2 шага.
    //    Если fast или fast.next окажется null — значит, список закончился
    //    обычным образом (тупиком), и цикла в нём нет.

    slow = slow.next;
    // 4. Черепаха делает один шаг.

    fast = fast.next.next;
    // 5. Заяц делает два шага (переходит через один узел).

    if (slow === fast) {
      // 6. Указатели встретились — значит, оба "забежали" в один и тот же
      //    узел, что возможно только если список закольцован.
      return true;
    }
  }

  return false;
  // 7. Заяц дошёл до конца списка (null) раньше, чем догнал черепаху —
  //    значит, цикла нет.
};
```

### Визуализация по шагам для списка с циклом `1 → 2 → 3 → 4 → (обратно на 2)`

| Шаг | slow (черепаха) | fast (заяц) | Встретились? |
|---|---|---|---|
| старт | `1` | `1` | — |
| 1 | `2` | `3` | нет |
| 2 | `3` | `2` (после круга по циклу) | нет |
| 3 | `4` | `4` | **да** → `true` |

Заяц как бы "накручивает круги" внутри цикла быстрее черепахи, и на каком-то шаге они неизбежно окажутся в одной и той же точке — как две стрелки часов с разной скоростью хода рано или поздно совпадают.

### Почему условие цикла именно `fast && fast.next`

Проверять нужно **оба** условия:
- `fast` — чтобы не обратиться к `.next` у `null` (если список закончился на нечётном шаге);
- `fast.next` — потому что `fast.next.next` тоже может упасть с ошибкой, если `fast.next` окажется `null`.

Обе проверки защищают от `TypeError: Cannot read properties of null` при попытке прыгнуть на 2 шага вперёд у короткого хвоста списка.

## Как устроена вспомогательная функция `createListWithCycle`

```js
const createListWithCycle = (arr, pos) => {
  if (arr.length === 0) return null;
  // 1. Пустой массив — пустой список, дальше строить нечего.

  const nodes = arr.map((val) => createNode(val));
  // 2. Сначала создаём ВСЕ узлы разом, пока ещё без связей между ними.
  //    На этом этапе у каждого узла next === null.

  nodes.forEach((node, index) => {
    if (index < nodes.length - 1) {
      node.next = nodes[index + 1];
    }
  });
  // 3. Затем проходим по уже созданным узлам и связываем их по порядку:
  //    node[0].next = node[1], node[1].next = node[2], и так далее.
  //    Последний узел (index === nodes.length - 1) не трогаем —
  //    у него next пока остаётся null.

  if (pos >= 0) {
    nodes[nodes.length - 1].next = nodes[pos];
  }
  // 4. Если pos указан (>= 0) — "замыкаем" список в цикл: последний узел
  //    начинает ссылаться не на null, а на узел с индексом pos.

  return nodes[0];
  // 5. Возвращаем голову собранного списка.
};
```

Этот подход (сначала создать все узлы, потом отдельным проходом связать их через `forEach`) отличается от альтернативного варианта "строить список сразу по ходу создания узлов", но даёт тот же результат — и удобен именно тем, что на шаге 4 уже есть доступ к любому узлу по индексу (`nodes[pos]`), что и нужно для организации цикла.

## Почему этот подход лучше, чем "запоминать посещённые узлы"

Альтернативное (более очевидное для новичка) решение — сложить все посещённые узлы в `Set` и на каждом шаге проверять, не встречался ли уже текущий узел:

```js
const hasCycleWithSet = (head) => {
  const visited = new Set();
  let current = head;

  while (current) {
    if (visited.has(current)) {
      return true;
    }
    visited.add(current);
    current = current.next;
  }

  return false;
};
```

Это решение тоже работает за O(n) по времени, но тратит O(n) **дополнительной памяти** на сам `Set`. Алгоритм Флойда решает задачу с той же скоростью, но за **O(1) памяти** — именно это и требуется в follow-up вопросе задачи ("решите задачу, используя только O(1) памяти").

## Сложность алгоритма

| Показатель | Значение |
|---|---|
| Время | O(n), где n — количество узлов в списке |
| Память | O(1) — используются только две переменные-указателя, независимо от размера списка |

## Частые ошибки при решении этой задачи

- Проверять только `while (fast)`, забыв про `fast.next` — на списке с чётным числом узлов без цикла код упадёт с ошибкой обращения к `.next` у `null`.
- Сравнивать значения узлов (`slow.val === fast.val`) вместо самих узлов (`slow === fast`) — в списке могут быть узлы с одинаковыми значениями, но без цикла, что даст неверный ответ `true` там, где должно быть `false`.
- Пытаться "распечатать" список с циклом через обычный обход (`while (current) { ... current = current.next }`) — если список действительно зациклен, такой обход никогда не завершится (бесконечный цикл в самом буквальном смысле). Поэтому в `task.js`/`solution.js` нет функции наподобие `linkedListToArray` — она была бы небезопасна для циклических списков.
- Забыть, что `pos` в условии задачи — это только способ **описать** входные данные для примеров, а не то, что реально передаётся в функцию. Внутри `hasCycle` доступен только `head`.
- Двигать `fast` на 2 шага, а `slow` тоже на 2 (по ошибке скопировав строку) — тогда указатели будут двигаться синхронно и никогда не встретятся, даже если цикл есть.
- В `createListWithCycle` забыть проверку `if (arr.length === 0)` — тогда `nodes[nodes.length - 1]` при пустом массиве обратится к несуществующему элементу (`nodes[-1]`), и функция вернёт `undefined` вместо ожидаемого `null`.
