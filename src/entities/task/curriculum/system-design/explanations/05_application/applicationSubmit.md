# Разбор задачи: «Отправка заявки без дублей»

## 1. Почему блокировки кнопки мало

Кнопка «Отправить» блокируется на время запроса, и двойной клик не создаст вторую заявку. Но есть случай, от которого кнопка не спасает:

1. Запрос дошёл до сервера, заявка создана.
2. Ответ потерялся: оборвалась мобильная сеть или истёк таймаут.
3. Клиент видит ошибку и повторяет запрос — сервер создаёт **вторую** заявку.

Клиент не знает, дошёл ли запрос. Безопасный повтор возможен, только если сервер умеет узнать повтор. Для этого запрос несёт **ключ идемпотентности**: сервер запоминает ключ и ответ на него, а повтор с тем же ключом получает уже созданную заявку.

## 2. Решение по шагам

### Шаг 1. Один промис на отправку

```ts
const submit = (values) => {
  if (inflight) return inflight;
  key ??= createKey();
  inflight = send(values, key)
    .then(...)
    .finally(() => {
      inflight = null;
    });
  return inflight;
};
```

Пока отправка идёт, повторный вызов возвращает тот же промис. Это защита от двойного клика на уровне логики, а не только кнопки.

### Шаг 2. Повторы с тем же ключом

```ts
for (let attempt = 1; attempt <= maxAttempts; attempt++) {
  if (attempt > 1) await wait(retryDelayMs);
  try {
    response = await fetch(url, { method: "POST", headers, body });
  } catch {
    continue;
  }
  ...
}
```

Сетевая ошибка и `5xx` — временные: повтор может пройти. Все попытки идут с одним ключом, поэтому даже если первая создала заявку, повтор вернёт её же.

### Шаг 3. Ответы, которые повторять нельзя

- `422` — данные не прошли проверку. Повтор даст тот же ответ, нужно показать ошибки у полей. Сервер присылает `{ field, code }`, а текст выбирает клиент по коду: так ошибка привязана к полю и переводится вместе с интерфейсом.
- Прочие `4xx` — ошибка в самом запросе (нет прав, неверный формат). Повтор тоже бесполезен.

### Шаг 4. Сколько живёт ключ

Ключ сбрасывается после `ok` (заявка принята) и после `422` (данные изменятся, это новая попытка). После `failed` ключ остаётся: возможно, одна из попыток всё-таки создала заявку, и повторная отправка должна её найти, а не создать вторую.

## 3. Подводные камни

- **Тот же ключ с другими данными.** Если после неудачи пользователь изменил форму, сервер получит прежний ключ с новым телом и обычно ответит ошибкой: ключ привязан к содержимому запроса. Поэтому перед отправкой изменённых данных стоит спросить у сервера, создана ли заявка, и только потом брать новый ключ.
- **Повторы без паузы и всем сразу.** При сбое сервера тысячи клиентов повторяют одновременно. В продакшене пауза растёт (backoff) и получает случайную добавку (джиттер), а ответ `429` с `Retry-After` уважается.
- **Ключ только на клиенте.** Ключ работает, только если сервер хранит ключи и ответы на них. Это договорённость с бэкендом, а не трюк фронтенда.
- **Таймаут.** Запрос без таймаута может висеть минутами. Для отправки стоит ограничить ожидание через `AbortSignal.timeout`.

## 4. Связь с реальными сервисами

Stripe и многие платёжные API принимают заголовок `Idempotency-Key`. Для него есть черновик стандарта IETF. TanStack Query повторяет мутации, если включить `retry`, но ключ идемпотентности нужно передать самому.
