# Разбор задачи: «Валидация формы по схеме»

## 1. Зачем схема

Форма заявки меняется чаще, чем выходят релизы: регулятор добавил поле, продукт запустил A/B-тест, у ипотеки свой набор шагов. Если поля и правила зашиты в код, каждое такое изменение — релиз фронтенда и ручная синхронизация с правилами на сервере.

Поэтому сервер присылает **схему**: список полей с правилами и условиями видимости. Клиент рендерит поля по ней и проверяет значения по тем же правилам, что и сервер. Клиентская проверка нужна для мгновенного отклика, а источник правды остаётся на сервере.

## 2. Решение по шагам

### Шаг 1. Что считать пустым

```ts
const isEmpty = (value: unknown): boolean =>
  value === undefined ||
  value === null ||
  (typeof value === "string" && value.trim() === "") ||
  (Array.isArray(value) && value.length === 0);
```

Строка из пробелов — пустая: иначе обязательное поле можно «заполнить» пробелом. Пустой массив — это ни одного выбранного варианта в группе чекбоксов.

### Шаг 2. Правила по порядку

Пустое значение проверяет только `required`. Остальные правила описывают формат введённого и для пустого поля не имеют смысла: необязательный комментарий не должен ругаться на `minLength`, пока его не начали писать.

Дальше правила проверяются по порядку, и возвращается первое нарушенное. У поля одна ошибка: пользователю нужен один понятный следующий шаг, а не список из трёх претензий.

`pattern` приходит строкой, потому что схема — это JSON. Объект `RegExp` создаётся на клиенте.

### Шаг 3. Видимость вычисляется, а не хранится

```ts
const isVisible = (field: FieldSchema | undefined): boolean => {
  if (!field?.visibleIf) return true;
  const { field: parent, equals } = field.visibleIf;
  return values[parent] === equals && isVisible(byName.get(parent));
};
```

Поле видно, если совпало его условие **и** видно поле, от которого оно зависит. Без второй проверки ИНН созаёмщика оставался бы обязательным, когда блок созаёмщика скрыт.

Видимость не хранится в состоянии: она выводится из схемы и значений. Хранимый флаг рано или поздно разойдётся с данными.

### Шаг 4. Что уходит на сервер

Значение скрытого поля остаётся в черновике: если пользователь вернёт прежний ответ, ввод не потерян. Но в заявку уходят только видимые поля схемы. Иначе сервер получит ИНН самозанятого у сотрудника по найму и может отклонить заявку из-за противоречия.

## 3. Подводные камни

- **Ошибка до ввода.** Валидатор считает ошибки всегда, но показывать их нужно по правилам интерфейса: после ухода с поля или при «Далее».
- **Циклы в схеме.** Если сервер пришлёт поля, которые зависят друг от друга по кругу, рекурсия не закончится. В продакшене схему проверяют на сервере или ограничивают глубину.
- **`new RegExp` на каждый вызов.** Для 40 полей это незаметно, но при проверке на каждое нажатие регулярные выражения стоит кэшировать по схеме.
- **Правила, которых нет у клиента.** ИНН в реестре, возраст по паспорту, кредитная история проверяются только на сервере. Клиентская проверка не заменяет серверную.

## 4. Связь с реальными библиотеками

`react-hook-form` и Formik принимают схему через резолверы (Zod, Yup). Zod-схему можно использовать на клиенте и на сервере на Node.js. JSON Schema с валидатором вроде Ajv — вариант, когда бэкенд не на JavaScript.

## 5. Что обсудить на интервью

- Когда схема с сервера оправдана, а когда достаточно полей в коде.
- Как синхронизировать правила клиента и сервера и что делать с правилами, которые знает только сервер.
- Почему видимость и валидность вычисляются, а не хранятся.
- Что происходит со значениями скрытых полей в черновике и в заявке.
