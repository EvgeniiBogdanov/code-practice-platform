# Разбор задачи: «Автосохранение черновика»

## 1. Зачем это в форме заявки

Заявку на кредит заполняют 10–15 минут, часто с телефона. Сел телефон, закрылась вкладка, пользователь решил продолжить вечером — без черновика всё введённое пропадает, и до отправки доходит меньше людей.

Сохранять на каждое нажатие плохо по двум причинам:

- **нагрузка**: десятки запросов в минуту от каждого пользователя;
- **гонки**: если два запроса идут параллельно, ответ старого может прийти последним и затереть новые данные.

Поэтому сохраняем после паузы в вводе, не больше одного запроса одновременно, и с версией черновика, чтобы сервер мог отклонить устаревшую запись.

## 2. Решение по шагам

### Шаг 1. Несохранённые значения и пауза

```ts
const change = (values: V): void => {
  pending = { values };
  if (timer !== null) clearTimeout(timer);
  timer = setTimeout(() => void flush(), delayMs);
};
```

`pending` хранит последние значения, которые ещё не ушли на сервер. Обёртка `{ values }` отличает «сохранять нечего» от значений, которые сами могут быть пустыми. Каждое изменение перезапускает таймер: серия нажатий даёт одно сохранение.

### Шаг 2. Один запрос за раз

```ts
const drain = async (): Promise<void> => {
  while (pending) {
    const { values } = pending;
    pending = null;
    onStatus("saving");
    ({ version } = await save(values, version));
  }
  onStatus("saved");
};
```

Цикл забирает несохранённые значения и ждёт ответа. Если за это время пришли новые изменения, цикл сохранит их следующим запросом. Параллельных запросов нет, поэтому порядок ответов совпадает с порядком изменений.

Версия из ответа сервера уходит в следующий запрос. Если черновик тем временем изменили в другой вкладке, сервер увидит старую версию и ответит конфликтом.

### Шаг 3. flush

```ts
const flush = (): Promise<void> => {
  if (timer !== null) clearTimeout(timer);
  timer = null;
  if (inflight) return inflight;
  if (!pending) return Promise.resolve();
  inflight = drain().finally(() => {
    inflight = null;
  });
  return inflight;
};
```

`flush` нужен при смене шага и перед отправкой: ждать паузу нельзя. Если запрос уже идёт, возвращаем его промис: цикл сам заберёт новые значения.

### Шаг 4. Отказ

При ошибке значения возвращаются в `pending`, но только если поверх не пришли новые: свежие изменения важнее неудачных. Статус `"error"` показывает пользователю «Не сохранено», а следующий `change` или `flush` повторит сохранение.

## 3. Подводные камни

- **Конфликт версий.** Ответ `409` нельзя повторять тем же запросом: он снова получит конфликт. Нужно загрузить актуальный черновик и спросить пользователя, какую версию оставить.
- **Закрытие вкладки.** Обычный `fetch` при закрытии страницы может не дойти. Для последнего сохранения подходят `fetch` с `keepalive: true` или `navigator.sendBeacon`, а событие — `visibilitychange`, а не `beforeunload`.
- **Повторы без паузы.** В реальном приложении повтор после ошибки стоит делать с паузой и растущим интервалом, а не при каждом нажатии.
- **Персональные данные.** Черновик заявки содержит паспорт и доход, поэтому хранится на сервере, а не в localStorage.

## 4. Связь с реальными библиотеками

TanStack Query даёт `useMutation` со статусами и повтором, но очередь сохранений и склейку изменений приходится писать самим: это и есть этот дрилл. Тот же подход используют редакторы документов: сохранение по паузе, одно в полёте, версия для конфликтов.

## 5. Что обсудить на интервью

- Почему сохранение по паузе, а не на каждое нажатие и не по кнопке.
- Как не дать старому ответу затереть новые данные.
- Что делать при конфликте двух вкладок или двух устройств.
- Где хранить черновик с персональными данными и почему не в localStorage.
