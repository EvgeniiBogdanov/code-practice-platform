# Разбор задачи: «WebSocket с переподключением и backoff»

## 1. Почему просто «переподключиться» нельзя

Соединение рвётся постоянно: смена сети, метро, деплой сервера. Наивный код переподключается сразу:

```ts
socket.onclose = () => connect();
```

Когда сервер перезапускается, **все** клиенты теряют связь одновременно и одновременно возвращаются. Сервер, который только что поднялся, получает лавину подключений и падает снова (**thundering herd**).

## 2. Экспоненциальная задержка и джиттер

- **Backoff.** Каждая неудачная попытка удваивает ожидание: 1 с, 2 с, 4 с … до потолка (`maxDelayMs`). Нагрузка на сервер быстро падает.
- **Джиттер.** Если все клиенты ждут ровно 1 с, 2 с, 4 с, волны остаются. Случайная часть размазывает подключения по времени. Вариант «полный джиттер»: задержка = `random() × потолок`.

```ts
const ceiling = Math.min(maxDelayMs, baseDelayMs * 2 ** attempt);
timer = setTimeout(connect, random() * ceiling);
```

`random` передаётся параметром, чтобы тест мог сделать поведение детерминированным: это обычный приём для кода со случайностью.

## 3. Решение по шагам

1. **Счётчик попыток** растёт при каждом обрыве и **сбрасывается после успешного `open`**. Иначе после долгой работы первое же переподключение ждало бы максимальное время.
2. **Очередь исходящих.** Пока сокет не открыт, `send` кладёт сообщение в массив, а `onopen` отправляет накопленное по порядку. Пользователь не теряет написанное.
3. **Флаг закрытия.** `close()` ставит `isClosed`, снимает таймер и закрывает сокет; обработчик `onclose` видит флаг и не планирует переподключение. Без этого вызов `close()` запускал бы новый цикл.
4. **Статусы** (`connecting` → `open` → `reconnecting` → … → `closed`) нужны интерфейсу: индикатор «Нет соединения», блокировка поля ввода.

## 4. Чего не хватает до продакшена

| Что | Зачем |
| --- | --- |
| Heartbeat (ping/pong) | Заметить «тихий» обрыв, когда `onclose` не пришёл |
| Догрузка пропущенных сообщений | После восстановления запросить всё после последнего полученного id |
| Реакция на `online` и `visibilitychange` | Не ждать таймер, когда сеть вернулась или вкладка снова открыта |
| Дедупликация | Сообщение могло прийти и из догрузки, и из потока |
| Лимит очереди | Не копить бесконечно сообщения в долгом офлайне |

## 5. Что обсудить на интервью

- WebSocket, SSE или long polling и когда что выбирать.
- Как авторизовать сокет: токен в первом сообщении, а не в URL (URL попадает в логи).
- Как масштабировать на сервере: sticky-сессии или брокер сообщений.
