# Сеть и real-time

Сеть — самая ненадёжная часть клиентского приложения: она медленная, прерывается и меняет поведение в зависимости от устройства. Хорошая архитектура исходит из этого.

## HTTP-кэширование

Лучший запрос — тот, который не пришлось отправлять.

| Заголовок                  | Что делает                                                     |
| -------------------------- | -------------------------------------------------------------- |
| `Cache-Control: max-age=…` | Браузер использует ответ без обращения к серверу, пока он свеж |
| `Cache-Control: no-store`  | Нельзя сохранять (личные и чувствительные данные)              |
| `ETag` / `If-None-Match`   | Условный запрос: сервер отвечает `304 Not Modified` без тела   |
| `stale-while-revalidate`   | Показать устаревшее сразу и обновить в фоне                    |

Типичная стратегия: статические файлы с хешем в имени получают `max-age` на год и `immutable`, а HTML и API — короткий срок или условные запросы.

## Устойчивость запросов

- **Таймауты.** Запрос без таймаута может висеть бесконечно.
- **Повторы.** Повторяйте идемпотентные запросы (GET, PUT), но не подряд: используйте экспоненциальную задержку (backoff) и случайную добавку (джиттер), иначе сервер получит волну повторов.
- **Отмена.** `AbortController` прерывает запрос при смене экрана или нового ввода.
- **Дедупликация.** Несколько компонентов, которым нужен один и тот же ресурс, делают один запрос.
- **Идемпотентность мутаций.** Клиентский идентификатор операции защищает от дублей при повторной отправке.

## Способы получать обновления

| Способ                       | Направление                                                | Когда подходит                                                  |
| ---------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------- |
| **Polling**                  | Клиент спрашивает по таймеру                               | Редкие обновления, простота важнее задержки                     |
| **Long polling**             | Клиент спрашивает, сервер отвечает, когда есть что сказать | Запасной вариант при ограничениях сети                          |
| **SSE** (Server-Sent Events) | Только сервер → клиент по HTTP                             | Уведомления, ленты, котировки; автопереподключение «из коробки» |
| **WebSocket**                | Двусторонний канал                                         | Чат, совместное редактирование, игры                            |

Выбирайте минимально достаточный механизм. SSE проще WebSocket: работает поверх обычного HTTP, хорошо проходит через прокси и балансировщики. WebSocket нужен, когда клиент тоже часто отправляет данные.

## Жизненный цикл соединения

Соединение real-time нужно **эксплуатировать**, а не только открыть:

- **Переподключение** с экспоненциальной задержкой и джиттером. Иначе после падения сервера все клиенты вернутся одновременно.
- **Heartbeat.** Периодический ping позволяет заметить «тихий» обрыв.
- **Догрузка пропущенного.** После восстановления запросите события после последнего полученного id.
- **Очередь исходящих.** Сообщения, написанные в офлайне, отправьте после подключения.
- **Реакция на среду.** События `online`, `offline` и `visibilitychange` позволяют не ждать таймер.
- **Дедупликация.** Сообщение могло прийти и из догрузки, и из потока.

## Офлайн и плохая сеть

Вопросы, которые стоит задать: что пользователь видит без сети? Что можно сделать офлайн? Как синхронизируются изменения? Варианты: показать кэш и пометить устаревшие данные, хранить очередь действий в IndexedDB, использовать service worker для статики. Для спорных случаев нужна стратегия разрешения конфликтов (последняя запись побеждает, слияние, ручной выбор).

## Что сказать на интервью

«Для чата беру WebSocket: двусторонний поток и низкая задержка. Для устойчивости: переподключение с backoff и джиттером, heartbeat, очередь исходящих и догрузка пропущенного по последнему id. Сообщения показываю optimistic со статусами, повтор доступен для неудавшихся. Для ленты уведомлений хватит SSE».
