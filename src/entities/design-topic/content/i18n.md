Интернационализация (i18n) — подготовка приложения к разным языкам и регионам. Локализация (l10n) — конкретные переводы и форматы для каждого из них. Инженерная задача здесь не в переводе, а в том, **где хранить строки, как выбрать язык и как не сломать вёрстку**.

## Что входит

- **Строки.** В коде только ключи, тексты — в словарях по языкам. Текст в компоненте невозможно перевести без правки кода.
- **Форматы.** Даты, числа и валюта через `Intl.DateTimeFormat` и `Intl.NumberFormat`. Формат, написанный руками, ломается в другом регионе.
- **Плюрализация.** В русском три формы («1 товар», «2 товара», «5 товаров»), в арабском шесть. Выбор формы делает `Intl.PluralRules`, а не `if`.
- **Направление текста.** RTL-языки (арабский, иврит): `dir="rtl"` и логические свойства CSS (`margin-inline-start` вместо `margin-left`).
- **Растяжение текста.** Немецкий и финский длиннее английского. Кнопки и меню должны переносить текст, а не обрезать его.

## Язык и валюта — разные оси

Мультиязычность и мультивалютность — независимые вопросы. Язык зависит от пользователя, валюта — от рынка и налогов. Для маркетплейса язык берут из URL или настроек, а валюту и налоги — из региона доставки.

## Как выбрать язык

Порядок приоритета: явный выбор пользователя (сохранён в cookie или в профиле) → язык в URL (`/ru/...`) → заголовок `Accept-Language` → `navigator.language` в браузере → базовая локаль. Под SSR язык определяют на сервере, чтобы первый экран не мигал сменой языка.

## Где хранить переводы

| Вариант                     | Плюсы                                 | Минусы                                              |
| --------------------------- | ------------------------------------- | --------------------------------------------------- |
| JSON в бандле               | Просто, работает офлайн               | Весь словарь уходит клиенту; смена перевода = релиз |
| Загрузка словаря по локали  | Меньше бандл, словарь кэшируется      | Задержка первого показа, нужен fallback             |
| Сервис переводов (TMS, CMS) | Переводчики работают без разработчика | Инфраструктура, кэш, согласованность версий         |

Словарь интерфейса грузят по локали и кэшируют. Описания товаров и статьи — это **данные**, а не строки интерфейса: их переводят на сервере и отдают по языку.

## Частые ошибки

- **Склейка строк.** `"Осталось " + n + " шт."` ломает порядок слов в других языках. Используйте плейсхолдеры: `"Осталось {count} шт."`.
- **Даты и валюта вручную.** Захардкоженный `₽` и формат `dd.mm.yyyy` ломают любой другой рынок.
- **Нет fallback.** Пропущенный ключ в одном языке показывает пустую строку или ключ вместо текста.
- **Текст внутри картинок.** Его не переведёшь и не прочитает скринридер.

## SEO для языков

Каждый язык — отдельный URL, в `<head>` — `hreflang` для альтернатив, в sitemap — ссылки между языками. Без этого поисковик покажет один язык всем пользователям независимо от их локали.

## Точки выбора

| Точка              | Альтернативы                              | Вопрос-критерий                            |
| ------------------ | ----------------------------------------- | ------------------------------------------ |
| Определение языка  | URL / cookie / `Accept-Language`          | Нужен ли SEO по языкам? Кто пользователь?  |
| Хранение словарей  | Бандл / загрузка по локали / сервис       | Как часто меняются тексты и кто их правит? |
| Направление текста | Только LTR / RTL с логическими свойствами | Есть ли рынки с RTL?                       |
| Валюта             | По языку / по региону                     | Один ценник для всех или локальные цены?   |

## Что сказать на интервью

«Строки вынесены в словари по локали, которые грузятся лениво. Даты, числа и плюрализацию делаю через `Intl`. Язык определяю по URL с fallback на `Accept-Language`, чтобы SSR отдавал правильный язык сразу. Валюту беру из региона, а не из языка».
